& Remediation

VulSolver · Problem

Addressing the Exposure Window at Scale

  • Growing number of critical vulnerabilities
  • Long-lived exposure windows
  • 400+ teams managing application security issues
  • Negative impact on time to market
[Juan Esteban, ~1.5 min] "Let me take you back to what vulnerability management looked like at Bancolombia before VulSolver. We had a growing number of critical vulnerabilities across our infrastructure and applications, including systems critical to the organization. Exposure windows were long-lived -- days, sometimes weeks. With over 400 teams involved in vulnerability closure, this fragmentation made it very difficult to maintain constant visibility and control. Security was reactive instead of proactive, with a negative impact on time to market and high operational risk. We knew we had to transform our approach."

VulSolver

VulSolver Workflow

1. Onboard Servers Register & enroll
2. Register in DB SQL / cloud database
3. Daily Assessment Tenable · EC2 + OnPrem
4. Schedule Workflows Automated pipelines
8. Dashboards Remediation activity
7. Log Activities Store for traceability
6. Scan & Remediate AAP · Patch & notify
5. Recovery Points Veeam · VMware snapshots
[Juan Esteban, ~2 min] "This is the VulSolver workflow -- it manages the complete vulnerability closure process. First, teams enroll in the solution to define their maintenance windows and ensure that when a machine requires a reboot, it happens after the patching process. That information is registered in a central database to control the automation. Then there's a daily assessment of which vulnerabilities are present on enrolled servers to measure remediation effectiveness. Next, workflows execute automatically based on approved change processes. The remediation actions have three parts: first, recovery points through Veeam and VMware Snapshots to ensure safe rollback if needed. Then a vulnerability scan and notification before the patching process. The patching itself runs automatically, and finally the status is reported back to the teams. All activities are stored for traceability and event correlation. Results are published on a dashboard so teams have full visibility of their vulnerabilities and the remediation actions taken, centralized in a single point of information. The key here is the full loop -- all automated. No tickets, no manual scheduling, no waiting."

Use Case 2 · Juan David

[TRANSITION — Juan Esteban to Juan David] "Thank you Juan Esteban. Our second use case is a completely different domain -- same platform, completely different challenge. Database & Cloud · Problem

The Challenge of Cloud Database Discovery

  • Challenges in tracking database services running on EC2
  • Dynamic AWS environment — instances come and go
  • Suboptimal database licensing efficiency
  • Bad practices on database management — no automated enforcement
[Juan David, ~1.5 min] "Bancolombia is a company where autonomy is a keyword. Technology teams deploy infrastructure through infrastructure as code, which is great -- but this autonomous approach creates a major challenge for database teams: maintaining an up-to-date inventory of databases implemented in the AWS cloud. We need this inventory to control database licensing, to track vulnerabilities on database services, and to ensure baseline compliance. Our AWS environment is dynamic -- instances come and go. Without accurate tracking, we couldn't optimize any of those. We found in Ansible a very powerful tool to solve this challenge automatically."

Database & Cloud · Success

Continuous Discovery and CMDB Integration

  • Dynamic inventories and scheduled API queries scan all EC2 instances
  • Detect DB services: Oracle, MS SQL Server, PostgreSQL and others across Linux & Windows
  • Auto-tagging with dbservice=true via cross-cutting role enables grouping
  • Positives registered in BMC Helix under EC2 category
AWS EC2 Dynamic inventory scanning
DB Discovery Validate services via API
EC2 Tagging dbservice=true · cross-cutting role
BMC Helix Register in EC2 category
[Juan David, ~2 min] "The use case we implemented in Ansible runs on an automatic schedule -- several times a day, every day of the week. Through dynamic inventories and scheduled API queries, the playbooks traverse all EC2 instances in the Bancolombia AWS environment, validating database services by passing IPs dynamically through the Ansible API. When a validation is positive -- meaning a database service is found -- the playbook tags the EC2 instance with a 'dbservice' label set to true. This uses a cross-cutting role we built for tagging across different use cases. That tag is the key. It lets us group all database EC2 instances together and kick off additional processes -- like retrieving engine versions, user permissions, and support extension status. The positive results are then registered in BMC Helix under the EC2 category, complementing the CMDB with accurate, up-to-date database information. We detect Oracle, MS SQL Server, PostgreSQL, and other engines across both Linux and Windows hosts. The same platform, the same standards -- completely different domain."

[Leonardo, ~3 min] "So you've just seen three very different use cases -- security remediation, database orchestration, and mainframe integration. Different domains, different teams, different challenges. But if you look underneath, there's a pattern. Five things made all of this work: First -- the Community of Practice. Open participation, cross-functional. The security team, the database team, the mainframe team -- they're not working in isolation. Second -- a governance model. They didn't try to build VulSolver on day one. They started with patching and hardening, proved the value, then expanded to automated remediation across platforms.
